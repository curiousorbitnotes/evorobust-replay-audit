# Impossible Code, Barely Changed Score: A Replay Study of Judge-Based Evaluation

Code and summary tables for the paper of the same name, NeurIPS 2026 Workshop on Self-Evolving Diversity-Driven Search for Robust AI Systems (EvoRobust).

Project page: https://curiousorbitnotes.github.io/evorobust-replay-audit/ | Paper: https://curiousorbitnotes.github.io/evorobust-replay-audit/assets/paper.pdf

## In one paragraph

We repeat an earlier coding evaluation on 421 HumanEval and MBPP problems. The base Qwen-2.5-7B-Instruct model still produces mostly parseable code, but the released CE-trained and SLJ-trained checkpoints produce invalid Python on 63%-67% of attempts. The strong judge's Pass@32 scores fall by only about 3 percentage points, from 96.67% to 93.95% for SLJ-trained. With 128 attempts per question, the judge accepts at least one SLJ-trained answer on 96.44% of problems, compared with 28.27% under execution tests. The paper recommends reporting the fraction of answers that pass Python's syntax check alongside every judge-based score.

## Units and the latest paper

Displayed score levels are percentages. Score differences and their confidence intervals are percentage points (pp). JSON summaries retain probabilities on the 0-1 scale for calculation, so multiply a score or difference by 100 for the paper's display units.

For the syntax gate, `replay_audit.json` preserves `delta = gated - judge` and its negative interval. The console and Table 11 show the positive drop `judge - gated`: negate the delta and reverse the negated interval bounds. This changes the reporting direction, not the underlying results.

The latest paper is available at https://curiousorbitnotes.github.io/evorobust-replay-audit/assets/paper.pdf. It includes both CE-trained and SLJ-trained scores and intervals, plus supporting tables for the comparison between runs, syntax gating, controlled bracket errors and MBPP naming.

### Summary provenance

Most files in `tables/` are outputs of the analysis scripts listed above. Three files are published snapshots derived from separately retained records and are not regenerated by those scripts:

- `temporal_ci_recomputed.json` records the between-run interval method, unrounded inputs, standard errors and input hashes. Appendix O gives the calculation.
- `judge_recheck_qwen_summary.json` selects the Qwen-only counts from the retained judge recheck. The earlier combined control summary remains a historical record.
- `mbpp_named_qwen_summary.json` contains the two Qwen Pass@128 values reported in Table 13, with source provenance. The named prompts produced new answers and do not replace the original evaluation outputs.

These snapshots keep scores on the 0-1 scale. The extra archived model controls are retained for provenance and future work, but are not reported as part of the current paper's three-checkpoint comparison.

## Recompute the Figure 1 curves

```
pip install -r requirements.txt
python scripts/evorobust_figure.py
```

This reads only `tables/`. It writes `figures/evorobust_fig1_replay.pdf` and `.png`, and refreshes `docs/assets/fig1_replay.png` from the same figure. Rates are percentages, and score differences are percentage points. Stored JSON values remain on the 0-1 scale. The figure uses hardened execution results from `paired_analyses.json`; `instruments.json` retains the study's cached-scorer execution results for comparison.

## Re-running the analyses

Run scripts from this folder. Inputs are read from these locations:

```
EVOROBUST_SAMPLES   <run>.samples.jsonl and <run>.slj_scores.jsonl   default: data/samples
EVOROBUST_ARCHIVE   earlier k=32 generations (replay audit only)     default: data/archive_k32
                    hardened per-sample results (from canon4/canon5) data/hardened_scores
                    the study's cached execution scores (.npy)       data/per_prompt_scores
                    weak-judge verdicts (wljdam_analyze.py)          data/wljdam   (or WLJDAM_DIR)
                    milder-corruption files (corrdose_*.py)          data/corrdose (or JUDGE_DIR for verdicts)
```

The paper's run tags are `base_qwen7b_code__code`, `ce_code_s1__code` and `slj_code_s1__code`.
A samples file has one JSON record per prompt (`prompt_idx`, `prompt`, `gold_answer`, `gold_tests`, `source`, `samples` with 128 strings). A verdict file has `prompt_idx` and `scores` (128 values).
The earlier k=32 archive (`EVOROBUST_ARCHIVE`) uses the same record layout with 32 samples per prompt, and its base-model file is named `base_qwen7b__code.samples.jsonl` (the trained runs keep their tags).
To produce the hardened per-sample results, run `canon4.py` for the base runs, then `CANON_RUNS=ce_code_s1__code,slj_code_s1__code CANON_TAG=trained python scripts/canon5.py` for the trained runs (`canon5.py` also reads `base_qwen7b_code__code.samples.jsonl` for its reference controls). The archived scripts include an additional base-model control that is not reported in the current paper. Each script states its own inputs at the top.

## Requirements

The parse counts and the error taxonomy were reproduced with CPython 3.10.2. Use Python 3.10 for exact reproduction: other Python versions can parse some code differently and word their syntax errors differently. Install the pinned packages in `requirements.txt`. The execution harness forks processes and needs Linux or macOS. The judge code needs `requests` and, for token-based truncation, `transformers` with the Qwen2.5 tokenizer (otherwise it falls back to character-based truncation, which changes the judge messages). The judges were served with vLLM (Qwen2.5-72B-Instruct and Qwen2.5-7B-Instruct, greedy decoding).

## Caveats

- The execution harness guards against accidental false passes and several known exploits. It is not a security boundary. Run untrusted code only in a sandbox.
- Pairing of cached judge verdicts to samples was checked on 1,280 Qwen base-model second-run answers. The Qwen-only counts in `tables/judge_recheck_qwen_summary.json` give 1,276 matching verdicts (99.69%). The earlier combined control summary remains in `tables/judge_recheck_summary.json` as a historical record. Pairing was not tested for the trained runs and is an assumption there.
- Between-run judge-score intervals use the unpaired normal approximation documented in Appendix O and `tables/temporal_ci_recomputed.json`. The first-run standard error comes from its aggregate Pass@32 score and 421 questions. The second-run standard error is the sample standard deviation of its 421 question-level Pass@32 estimates divided by sqrt(421). The retained input paths and hashes are recorded in that table. These intervals are separate from the within-run paired bootstrap intervals.
- `rewards/code_execution.py` is the study's cached scorer, kept exactly as used. It is looser than the native benchmark assertions in two known ways: a scalar can match a one-element expected list, and `is True` / `is False` / `is None` checks are evaluated as value equality. The paper's execution numbers come from the hardened harness (`canon4.py`, `canon5.py`), not from this scorer.
- `rewards/_extract.py` normalizes math answers through floating point, so very large integers that differ only beyond double precision compare equal. The paper uses only the code domain.
- The evidence comes from one training and release pipeline, and the cause of the replay discrepancy is unresolved.
